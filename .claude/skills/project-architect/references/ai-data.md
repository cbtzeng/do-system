# AI/資料專案 技術範本

## 典型分層與職責
- **資料來源/擷取**：來源串接、爬取、上傳、ETL/ELT 管線。
- **資料儲存**：資料倉儲（BigQuery/Snowflake/Redshift）、資料湖、向量資料庫（pgvector/Pinecone/Qdrant）。
- **模型/推論層**：呼叫 LLM API（OpenAI/Anthropic 等）、或自建/微調模型、RAG 檢索、prompt 工程。
- **應用層**：把 AI 能力包成 API 或介面給使用者用。
- **評估與監控**：輸出品質評估、成本監控、資料漂移、回饋迴路。

## 技術選型參考
| 需求情境 | 建議方向 |
| 文件問答/知識庫 | RAG：文件切分 + 嵌入 + 向量檢索 + LLM 生成 |
| 自動化/Agent | LLM + 工具呼叫 + 流程編排，明確定義可控邊界 |
| 資料分析/儀表板 | ETL + 資料倉儲 + BI 工具(Metabase/Superset/Looker) |
| 預測/分類模型 | 特徵工程 + 訓練管線 + 模型服務 + 監控 |
| 既有資料整合 | 釐清資料品質與權限，整合成本常被低估 |

## 常見模組清單（拆解起點）
- 資料盤點與可行性驗證（POC）
- 資料管線：擷取、清洗、轉換、排程
- 資料儲存建置：倉儲/向量庫設定與 schema
- 模型/推論：prompt 設計、RAG 檢索、模型串接或訓練
- 評估機制：品質指標、測試集、人工審核介面
- 應用整合：API/介面、與既有系統串接
- 成本與監控：用量追蹤、告警、降本機制
- 部署與維運

## 複雜度判準
- **低**：單純串 LLM API、固定 prompt、無需自有資料、輸出容忍度高。
- **中**：RAG/中等資料管線、需資料清洗、有評估需求、單一資料源。
- **高**：自建/微調模型、多源異質資料整合、嚴格品質/合規要求、Agent 多步流程、資料品質差需大量處理。

## 估價提醒
AI/資料專案最大風險是「資料品質與可用性」與「輸出品質達標」，這兩項不確定性高，建議在風險一節明確標註，並在估價時給較高緩衝（見 effort-estimator）。POC/可行性驗證常需獨立成一個前置模組。
