# 專案架構設計 (Project Architect)

把一個專案想法或需求描述，轉成一份結構化、可被估價的技術架構藍圖。這份藍圖的核心價值在於「把模糊的需求拆成具體、可估工時的模組」，所以輸出要讓 effort-estimator skill 能直接接手。

## 何時用、怎麼開場

使用者通常會給你一段需求、一個點子、或一份既有文件。你的第一步是判斷專案屬於哪一類，因為不同類別的技術骨架差很多：

- **軟體/Web 系統開發** → 讀 `references/web.md`
- **AI/資料專案** → 讀 `references/ai-data.md`
- **App/行動應用** → 讀 `references/app.md`

一個專案可能橫跨多類（例如「有 App 也有後台也有 AI 推薦」），這時把相關的 reference 都讀進來，分別套用。

開始前，若以下資訊缺漏且影響架構判斷，先簡短問清楚（一次問完，不要逐題打擾）：使用者規模/併發量級、是否要串接既有系統、平台範圍（Web/iOS/Android）、資料敏感度與合規需求、上線時程壓力。如果使用者說「先抓個大概」，就用合理假設往下做，並把假設明確寫進輸出的「假設與前提」一節。

## 輸出格式

一律輸出成 Markdown 檔（存到使用者資料夾），用以下結構。這個結構是刻意設計的：前半段幫使用者確認「我們對需求的理解對不對」，後半段「模組拆解」直接餵給估價。

```markdown
# [專案名稱] 技術架構藍圖

## 1. 專案概述
一段話講清楚要解決什麼問題、給誰用、核心價值。

## 2. 需求摘要
- 功能性需求：條列使用者實際要的功能
- 非功能性需求：效能、可用性、安全、擴充性的具體目標

## 3. 系統架構
整體分層（前端 / 後端 / 資料 / 基礎設施 / 第三方），用文字描述各層職責與彼此關係。
若有助理解，附一段 mermaid 架構圖。

## 4. 技術選型
| 層級 | 選用技術 | 理由 |
列出每層的技術選擇與「為什麼選它」——理由要連結到需求（規模、團隊熟悉度、成本、時程）。

## 5. 模組拆解（估價用）
這是最重要的一節。把專案拆成可獨立估工時的模組，每個模組標註複雜度。
| 模組 | 說明 | 複雜度(低/中/高) | 主要工作項 |
複雜度判斷依據寫在 references 各檔，照那個基準走，估價才會一致。

## 6. 資料流與整合
關鍵資料怎麼流動、要串哪些第三方/既有系統、介接方式（API/Webhook/檔案）。

## 7. 風險與假設
- 技術風險與緩解方向
- 本架構所依據的假設（規模、時程、既有資源）——估價的緩衝會參考這裡
```

## 拆模組的原則

模組拆解的好壞直接決定估價準不準，掌握幾個原則：

每個模組應該大到「值得單獨列一行報價」、小到「能估出一個合理工時區間」。太細會讓報價單瑣碎，太粗會讓客戶看不出價值也讓估算失準。一般一個中型專案落在 8–20 個模組之間。

把跨模組的共用工作（環境建置、CI/CD、登入權限、共用元件庫）獨立成基礎建設模組，不要分攤到各功能裡，否則會重複計算或漏算。

複雜度標註要克制：不是功能聽起來厲害就是高複雜度，而是看實作不確定性、整合點數量、邊界情況多寡。各 reference 檔有該領域的複雜度判準，照著走。

## 銜接下一步

輸出完成後，主動告訴使用者下一步可以用 effort-estimator skill 把第 5 節的模組拆解轉成工時與成本估算。如果使用者接著要估價，「模組拆解」那張表就是直接輸入。
