# 工時成本估算 (Effort Estimator)

把模組清單換算成「要做多久、要花多少錢」。估算的價值在於可信與可解釋——每個數字都要能對客戶交代怎麼來的，所以方法要一致、假設要透明。

## 計價模型（已依使用者設定固定）

- **計價方式**：人天（man-day）× 日費率，並以模組為單位分項呈現。
- **幣別**：TWD（新台幣）。
- **稅**：營業稅 5%，報價需同時呈現未稅小計、稅額、含稅總計。

日費率若使用者未指定，先問清楚（可分角色，例如 PM/資深工程師/工程師/設計），或使用使用者提供的預設費率。沒有任何資訊時，用佔位費率並明確標註「待確認」，不要憑空假裝精確。

## 估算流程

### 1. 取得模組清單
理想輸入是 project-architect 的「模組拆解」表（含複雜度）。若使用者只給一句話或粗略清單，先快速補成模組清單再估——必要時建議先用 project-architect。

### 2. 逐模組估人天
依複雜度給人天區間，再取點估值。基準見 `references/estimation-guide.md`（含各複雜度的人天參考、各領域調整係數）。重點原則：

用「區間 + 點估」而非單一數字，區間反映不確定性。複雜度越高、規格越不明，區間越寬。把估算依據（參考了哪個基準、為何偏高/偏低）記下來，之後報價要解釋。

### 3. 加上專案層級的附加工時
純功能開發工時之外，這些幾乎一定會發生、卻最常被漏估：

- **專案管理 (PM)**：通常為開發工時的 10–15%
- **測試與 QA**：10–20%（品質要求高者更多）
- **溝通/會議/驗收修改**：5–10%
- **風險緩衝 (contingency)**：依整體不確定性 10–25%，AI/資料或規格不明的專案取高值

這些用百分比加成，並在輸出中分項列出，讓客戶看得到也好談。

### 4. 計算成本與稅
人天 × 日費率得各模組金額，加總得未稅小計，× 5% 得稅額，相加得含稅總計。**一律用 `scripts/calc_estimate.py` 計算**，不要手算——腳本保證加總、加成、稅額一致正確，並輸出乾淨的結構化結果。

```bash
python scripts/calc_estimate.py input.json
```
input.json 格式與用法見腳本檔頭註解與 `references/estimation-guide.md`。腳本會輸出含各模組金額、附加項、未稅/稅/含稅總計的 JSON。

### 5. 輸出估算表
產出兩種：給內部看的明細，與給客戶看的摘要。明細存成 Excel（用 xlsx skill）方便調整；摘要直接餵給 quote-builder。表格結構：

```
模組明細：| 模組 | 複雜度 | 人天(低-高) | 採用人天 | 角色/費率 | 金額(未稅) |
附加項：  | 項目(PM/QA/緩衝...) | 比例 | 金額 |
總計：    未稅小計 / 營業稅5% / 含稅總計
工期：    估算總人天 → 換算日曆工期（考慮並行與人力配置）
```

## 工期換算

總人天不等於日曆天。換算時考慮投入人力數與可並行程度：例如 60 人天、2 人並行、可並行度約 0.8，約為 60 /（2×0.8）≈ 38 個工作天。把人力配置假設寫清楚，這也是報價時程的依據。

## 常見錯誤（自我檢查）

估算完回頭檢查：是否漏了基礎建設/環境/上線的工時？緩衝是否與風險匹配（高風險卻只給 10% 是危險的）？費率是否還是佔位待確認？工期是否誤把總人天當日曆天？這些是報價失準的主因。

## 銜接下一步

輸出後告訴使用者下一步可用 quote-builder skill 把估算轉成正式 PDF 報價單與提案簡報。摘要表（模組、金額、未稅/稅/含稅、工期）就是 quote-builder 的直接輸入。
